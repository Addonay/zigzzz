# XML parser choices reward matching workloads

*Source snapshot: 21 October 2026. Research only; no application changes or benchmarks were performed.*

**quick-xml is a strong streaming XML parser, but the available evidence does not establish it as faster, smaller or more robust than current Expat, pugixml or original C++ RapidXML across equivalent workloads.** It fits selective extraction, including spreadsheet XML, because it can process events without constructing a complete document tree. Expat offers a similarly useful streaming architecture through a C interface that already fits this Zig application. Pugixml offers convenient tree navigation, editing and XPath; RapidXML emphasizes in-place tree construction; libxml2 offers substantially broader XML facilities. Their different responsibilities make many published speed comparisons misleading. Calamine uses quick-xml, but Calamine’s spreadsheet-format support comes from its surrounding implementation, not from the XML parser alone.

## Streaming and tree construction solve different problems

quick-xml is a Rust pull reader: application code requests the next event and decides what to retain. Reading an in-memory slice can borrow the original bytes; buffered reading reuses a caller-supplied buffer. Retaining an event as owned data introduces allocation. Its base Reader does not resolve namespaces; NsReader adds that responsibility. Optional integrations include async I/O, character decoding and Serde. These facilities make it attractive for extracting selected elements without paying for a general tree. ([quick-xml Reader](https://docs.rs/quick-xml/0.42.0/quick_xml/reader/struct.Reader.html), [event ownership](https://docs.rs/quick-xml/0.42.0/quick_xml/events/enum.Event.html#lifetime), [features](https://docs.rs/quick-xml/0.42.0/quick_xml/))

Expat reverses control: it pushes callbacks while consuming incremental input. That difference affects application structure, not automatically throughput. Both approaches can discard irrelevant XML as it passes. **Neither makes an entire XLSX import constant-memory**: shared strings, retained cells, ZIP buffers and application data structures still occupy memory. Expat provides namespace processing and configurable resource protections without requiring a DOM. ([Expat API](https://libexpat.github.io/doc/api/latest/))

The comparison below describes architectural fit and documented capabilities, rather than a performance ranking.

| Library | Model and language | Useful capabilities | Main tradeoff for this app |
|---|---|---|---|
| quick-xml | Rust pull/event reader and writer | Borrowed events, selective extraction, optional namespaces, Serde and async | Rust build/interface; checking and decoding options require attention |
| Expat | C streaming callbacks | Incremental extraction, namespaces, entity handling and resource controls | Application owns spreadsheet interpretation and retained data |
| pugixml | C++ mutable DOM | Editing, serialization, XPath 1.0, encoding conversion | Full tree storage; intentionally incomplete strictness |
| Original RapidXML | C++ in-place DOM | Compact integration and borrowed names/values | Input lifetime/mutation requirements; limited XML facilities and permissive defaults |
| libxml2 | C DOM, SAX and pull reader | XPath, DTD and XSD validation, broader XML toolkit | More configuration and capability than straightforward cell extraction needs |
| roxmltree | Rust read-only tree | Namespace-aware navigation, positions and references | Retains a tree; no editing or serialization |
| xmlparser | Rust tokenizer | Borrowed tokens with no parser allocations | Caller must implement structural correctness and higher-level behavior |

Pugixml supports immutable-input and in-place loading, with the latter requiring the input to outlive the document. RapidXML normally modifies its input and stores pointers into it. Borrowing reduces string copies, but DOM node storage and input retention remain. Pugixml’s conveniences are valuable when the application revisits arbitrary nodes or changes XML; they are less compelling when each worksheet row is consumed once. ([pugixml quick start](https://pugixml.org/docs/quickstart.html), [RapidXML manual](https://rapidxml.sourceforge.net/manual.html))

## Published benchmarks do not identify a current winner

**No modern apples-to-apples benchmark covering these libraries with equivalent work and checking was found in this research.** That does not imply equal speed. It means a numerical ranking would exceed the evidence.

quick-xml’s current comparison project primarily tests Rust libraries. Its low-level benchmark counts start and empty elements, separates borrowed-input and buffered reading, and explicitly disables `check_end_names` in both quick-xml cases. It does not build equivalent spreadsheet cells, decode every attribute or include ZIP processing. The dependency called `rapid-xml` in that project is a Rust crate: it is **not a benchmark of classic C++ RapidXML**. The comparison README explains how to generate Criterion results but supplies no current hardware/version results table. ([benchmark implementation](https://raw.githubusercontent.com/tafia/quick-xml/master/compare/benches/low-level.rs), [comparison dependencies](https://raw.githubusercontent.com/tafia/quick-xml/master/compare/Cargo.toml), [instructions](https://raw.githubusercontent.com/tafia/quick-xml/master/compare/README.md))

Pugixml’s published cross-library comparison uses Visual Studio 2015, an Intel Core i7 at 2.67 GHz and nine documents of approximately 1–20 MB. It measures parsing from memory and reports minimum repeated times. DOM implementations construct trees while SAX implementations receive dummy callbacks and pull implementations consume events. Those results are useful historical evidence, but neither current software nor equal application output is represented. ([pugixml benchmark methodology](https://pugixml.org/benchmark.html))

RapidXML’s familiar speed headline is older still: its manual compares a 50 KB document using fastest configurations, circa-2007 tools and processors, and pugixml 0.3. It cannot establish superiority over current pugixml or quick-xml. ([RapidXML performance section](https://rapidxml.sourceforge.net/manual.html#section_performance))

There is more concrete Rust evidence, with limitations. The roxmltree README reports Apple M1 Pro times of 1.250 ms for quick-xml versus 1.495 ms for roxmltree on its large document, and 0.206 ms versus 0.421 ms on its medium document. However, its benchmark manifest uses quick-xml 0.30, and the implementations differ in functionality. These are reported measurements of those cases, not predictions for quick-xml 0.42 or XLSX imports. ([reported results](https://raw.githubusercontent.com/RazrFalcon/roxmltree/master/README.md), [benchmark versions](https://raw.githubusercontent.com/RazrFalcon/roxmltree/master/benches/Cargo.toml))

The defensible interpretation is that quick-xml is competitive for selective reads and that avoiding unnecessary tree construction is promising. Whether it improves this application depends on how much time currently belongs to XML processing, decompression, string allocation and value conversion.

## Robustness requires four separate questions

**Well-formedness, schema validity, memory safety and resource safety are different properties.** Matching opening and closing tags concerns well-formedness. Checking a document against an XSD or DTD adds validity requirements. Preventing invalid memory access does not ensure either property. Preventing excessive CPU, allocation or external-resource access is another responsibility. The XML standard distinguishes well-formed documents from valid documents; libxml2 exposes separate schema-validation APIs. ([W3C XML specification](https://www.w3.org/TR/xml/), [libxml2 schema API](https://gnome.pages.gitlab.gnome.org/libxml2/html/xmlschemas_8h.html))

quick-xml 0.42 defaults to checking end-tag names, rejects unmatched closing tags and dangling ampersands, but disables comment correctness checks by default. Its changelog records UTF-8 validation when constructing events, namespace-specific limits and a Serde recursion limit. Those latter protections belong to the relevant APIs, and should not be attributed automatically to every plain Reader consumer. Version 0.42 uses DecodingReader for non-UTF-8 input rather than making an encoding feature switch equivalent to universal transparent decoding. ([configuration](https://docs.rs/quick-xml/0.42.0/quick_xml/reader/struct.Config.html), [0.42 changes](https://github.com/tafia/quick-xml/blob/master/Changelog.md#0420----2026-08-22))

Current Calamine source declares quick-xml `^0.42` with the encoding feature. Its XLSX helper constructs a buffered Reader and explicitly disables end-name checking and comment checking, preserves text whitespace, and expands empty elements. **Calamine and quick-xml’s benchmark therefore disable a check that default quick-xml enables.** That permits mismatched names at this parser layer; it does not mean every syntax check or spreadsheet consistency check disappears. Enabling the encoding feature alone also does not establish coverage of every workbook encoding: this research did not audit all Calamine decoding paths. ([Calamine dependencies](https://github.com/tafia/calamine/blob/master/Cargo.toml#L24), [XLSX reader configuration](https://github.com/tafia/calamine/blob/master/src/xlsx/mod.rs#L2704-L2709))

Rust prevents broad classes of memory mistakes in safe code, but not algorithmic denial of service. For example, RUSTSEC-2026-0194 concerns quadratic duplicate-attribute processing and is fixed from quick-xml 0.41.0. Its applicability depends on attribute checking and namespace-reader use. A CPU-bound expansion or checking loop also cannot be controlled simply by an I/O timeout. ([RustSec advisory](https://rustsec.org/advisories/RUSTSEC-2026-0194.html))

Pugixml deliberately permits some malformed constructs and does not expand DOCTYPE-defined entities; its XPath uses qualified names rather than namespace-expanded names. Original RapidXML omits DTD processing and does not check matching closing names by default; an explicit flag or `parse_full` enables that check. These are meaningful semantic differences when comparing speed. They do not prove either implementation crashes on malformed input. ([pugixml manual](https://pugixml.org/docs/manual.html), [RapidXML manual](https://rapidxml.sourceforge.net/manual.html))

Expat does not fetch external files or URLs unless the application supplies external-entity handling. Its current security documentation describes entity-amplification, allocation and reparse protections. libxml2 provides explicit controls including `XML_PARSE_NO_XXE`; confusingly, `XML_PARSE_NOENT` enables entity substitution, and `XML_PARSE_NONET` is not a complete XXE defense. A library with more features can expose more options that require careful configuration. **CVE counts alone cannot rank security**, and this research did not audit the app’s installed version or options. ([Expat security](https://libexpat.github.io/doc/xml-security/), [libxml2 parser options](https://gnome.pages.gitlab.gnome.org/libxml2/html/parser_8h.html))

## Size and capabilities favor different candidates

“Small” must specify source distribution, dependencies, linked executable increment or runtime memory. Pugixml’s one implementation file and two headers, or RapidXML’s single principal header, describe packaging rather than deployed code size. Compiler optimization, optional features, dead stripping, target and static versus dynamic linking change the result. No comparable numerical binary-size ranking was established here.

quick-xml has empty default Cargo features and memchr as its mandatory normal dependency; optional functionality adds dependencies. Pugixml can disable XPath, STL and exceptions and offers a compact DOM mode. These are useful tuning controls, but do not establish which yields the smallest Zig executable. Both Rust and C++ choices require a suitable bridge from Zig and their language build machinery; Expat and libxml2 already offer C interfaces. ([quick-xml manifest](https://raw.githubusercontent.com/tafia/quick-xml/master/Cargo.toml), [pugixml configuration](https://raw.githubusercontent.com/zeux/pugixml/v1.16/src/pugiconfig.hpp))

roxmltree is attractive for read-only navigation: it resolves namespaces, preserves positions and avoids unsafe code and dependencies. Its documented options reject nonempty DTDs by default, allow a node limit and expose an optional external-entity resolver. Those are API choices, not an unrestricted safety guarantee. xmlparser goes smaller conceptually: it tokenizes borrowed input without allocations, but deliberately omits matching-tree and duplicate-attribute checks. Its authors do not recommend using it directly as a complete XML parser. ([roxmltree](https://github.com/RazrFalcon/roxmltree), [parsing options](https://docs.rs/roxmltree/latest/roxmltree/struct.ParsingOptions.html), [xmlparser](https://github.com/RazrFalcon/xmlparser))

libxml2 earns its broader integration when requirements include XPath, streaming reading and schema validation together. That capability is unnecessary overhead in design and configuration if all the app needs is worksheet values. ([pull reader](https://gnome.pages.gitlab.gnome.org/libxml2/html/xmlreader_8h.html), [XPath](https://gnome.pages.gitlab.gnome.org/libxml2/html/xpath_8h.html))

## Conclusion

For this Zig app, keep Expat until measurements identify a meaningful bottleneck or maintenance problem. The current reader loads the ZIP into memory, extracts XML buffers and copies cell strings into an arena; Expat’s streaming capability does not make that whole pipeline a streaming importer. Changing the parser alone leaves those retention costs in place. Choose quick-xml for a Rust-based selective-extraction implementation; consider Calamine separately for complete spreadsheet support. Choose pugixml for mutable trees and XPath, roxmltree for read-only trees, and libxml2 for broader validation requirements. Original RapidXML merits consideration for controlled inputs with explicit checking and lifetime rules; xmlparser is a foundation for building a parser. Replacing the XML component alone will not supply Calamine’s workbook formats or spreadsheet semantics.

A useful future experiment would compare identical extracted worksheet XML and complete XLSX imports separately, using representative real files plus controlled malformed/resource-stress cases. Each implementation should return exactly the same cells and normalized strings, with documented encoding, entity and structural-checking behavior. Record pinned versions, optimized builds, machine details, repeated-run distributions, allocations, peak memory and stripped executable-size deltas; isolate decompression and distinguish warm-cache from cold-cache timings. That would answer the practical question: whether the migration saves enough import time, memory or maintenance effort to justify its additional integration.
